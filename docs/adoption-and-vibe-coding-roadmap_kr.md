# TraceLens 보급과 바이브 코딩 활용을 위한 개선·구현 계획

작성·검토 기준: 2026-09-08 10:43 KST다. 저장소 기준 커밋은 `b3d620e`다.

이 문서는 현재 소스와 공식 외부 자료를 조사하여 작성한 개발 제안서다. 아래의 새 명령, API, 타입, 화면은 **구현할 계약의 초안**이며 현재 제공되는 기능을 의미하지 않는다. 이번 작업은 문서 작성이며 제품 코드를 변경하거나 빌드·런타임 재현을 수행하지 않았다. 코드에서 확인한 동작, 그 동작에서 도출한 위험, 제품 가설을 구분한다.

## 1. 권고하는 방향

TraceLens의 다음 목표를 **“ASP.NET Core 요청을 이해하고, AI에 근거를 전달하고, 수정 영향을 확인하는 로컬 개발 도구”**로 잡는다.

여섯 가지 시각화와 DB·캐시·보상 처리 분석은 이미 있다. 사용자가 가치를 느끼려면 다음 흐름이 짧고 믿을 만해야 한다.

1. 소개를 보고 자신의 어떤 문제를 해결하는지 이해한다.
2. 복잡한 개발 환경 준비 없이 실행하고 예제를 탐색한다.
3. 자신의 API를 분석하여 실제 호출 위치와 분석 한계를 확인한다.
4. 선택한 작업에 필요한 문맥을 평소 사용하는 AI 에이전트에 전달한다.
5. AI가 코드를 수정한 뒤 명시적으로 재분석하여 영향과 남은 점검 항목을 확인한다.

가장 먼저 추진할 묶음은 **첫 사용 안내·영어 UI, 배포 패키지, Minimal API 지원, 신선도·분석 범위 개선, AI 문맥 묶음**이다. 그다음 변경 영향과 분석 전후 비교를 붙인다. 새 다이어그램 종류, 자체 코드 편집기, 다수 AI 공급자 직접 호출은 후순위로 둔다.

### 유지해야 할 설계 경계

정본인 [CLAUDE.md](../CLAUDE.md)의 제약을 유지한다. 단계 문서는 6단계 완료 후 삭제되어 현재 상태는 코드와 변경 이력으로 확인했다.

- 호출 흐름은 HTTP 진입점을 기준으로 단계적으로 탐색한다. 영향받는 여러 진입점은 목록으로 보여주고 하나를 선택하여 기존 그래프에서 연다.
- 호출 엣지는 메서드·생성자 호출만 표현한다. DI는 호출 해석에 사용하고, 이벤트·메시지 구독 관계를 새 호출 엣지로 만들지 않는다.
- 기존 클래스·전체 흐름도의 밀도 조절과 150개 임계치를 유지한다. 기존 시작 흐름·DB·캐시·미들웨어의 별도 분석 예외도 유지한다.
- 재분석은 사용자 버튼이나 명시적 실행 요청으로만 한다. 신선도 확인은 재분석을 실행하지 않는다.
- 서버는 루프백에만 바인딩하고 MCP는 로컬 stdio를 유지한다. 파일 트리 탐색기를 추가하지 않는다.
- CI의 생성·수정·실행·진단은 이번 작업과 구현 계획의 실행 범위에서 제외한다. 검증은 로컬 명령과 수동 배포 절차를 기준으로 기술한다.

## 3. 외부 조사에서 얻은 판단

### 3.1 “그래프 + AI”만으로 차별화를 설명하기 어렵다

NDepend는 호출자를 통한 영향 범위 탐색을 제공하며, 별도의 공식 MCP 서버도 공개했다. MCP 서버에는 의존 관계·소스·문제 조회와 기준 분석 대비 변경 관련 기능이 있다. 해당 서버는 NDepend API의 별도 평가판 또는 라이선스를 필요로 한다. 따라서 TraceLens의 소개에서 관련 도구가 없다고 단정하는 문구를 제거하는 편이 타당하다. [NDepend 영향 분석](https://www.ndepend.com/docs/refactoring-impact-analysis), [NDepend 공식 MCP 저장소](https://github.com/ndepend/NDepend.MCP.Server)를 근거로 한다.

TraceLens는 현재 MIT 라이선스의 자체 Roslyn 분석기를 갖추고 있다. ASP.NET Core 요청 중심의 탐색, 로컬 분석, 소스 근거를 가진 AI 전달, DB·캐시·보상 처리 확인을 쉬운 사용 흐름으로 묶는 데 집중한다. 이는 경쟁 제품보다 우월하다는 검증 결과가 아니라 제품 포지셔닝 제안이다.

### 3.2 AI에는 전체 그래프보다 작업에 맞는 제한된 문맥이 필요하다

Aider의 repository map은 중요한 심볼·시그니처를 추리고, 관련성과 토큰 예산에 맞춰 문맥을 구성한다. TraceLens도 같은 원칙을 요청 경로·호출 지점·점검 근거에 적용할 수 있다. 전체 `graph.json`을 매 질문에 붙이는 방식은 피한다. [Aider 공식 repository map 설명](https://aider.chat/docs/repomap.html)을 참고한다.

### 3.3 분석 근거와 검증 경험을 제품 가치로 삼을 이유가 있다

2025 Stack Overflow 설문은 AI 출력 정확성을 불신한다는 응답 46%, 신뢰한다는 응답 33%를 보고한다. 이 결과는 설문 응답자의 인식이며 TraceLens 수요·성능을 직접 입증하지는 않는다. 그래도 출처·누락 범위·수정 후 점검을 쉽게 확인하게 만드는 방향을 뒷받침한다. [설문 원문](https://survey.stackoverflow.co/2025/ai)을 근거로 한다.

AI 생산성은 도구·작업·사용자에 따라 달라진다. METR의 2026-02-24 후속 설명도 최신 실험의 선택 편향과 시간 측정 한계를 명시한다. 과거 연구의 속도 수치를 현재 도구 전체나 TraceLens에 적용하지 않는다. “토큰 80% 절약”, “개발 속도 두 배” 같은 홍보는 자체 측정 전에는 사용하지 않는다. [METR 후속 연구 설명](https://metr.org/blog/2026-02-24-uplift-update/)을 참고한다.

### 3.4 표준 연동과 배포 방식을 활용할 수 있다

VS Code는 로컬 MCP 서버와 서버가 제공하는 도구·프롬프트를 지원한다. 모든 에이전트의 실행기를 앱 안에 만드는 것보다, 공통 MCP와 복사 가능한 문맥을 먼저 개선하는 편이 구현 범위를 줄인다. 도구 결과는 MCP의 `structuredContent`와 출력 스키마에 맞춰 검증 가능하게 구성한다. [VS Code 공식 MCP 문서](https://code.visualstudio.com/docs/agent-customization/mcp-servers), [MCP 도구 명세 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)를 참고한다. 명세의 해당 기능을 근거로 사용하며, 이 버전을 최신이라고 단정하지 않는다.

.NET tool은 NuGet 패키지로 만들고 전역 또는 로컬 도구로 설치할 수 있다. 이를 주 배포 후보로 검토하되, Roslyn/MSBuild와 웹 정적 파일까지 포함한 실제 패키징 검증이 선행되어야 한다. [Microsoft .NET tool 제작 문서](https://learn.microsoft.com/en-us/dotnet/core/tools/global-tools-how-to-create)를 참고한다.

조사에는 agent-reach의 검색·웹 자료 조사 지침을 적용했다. 로컬 실행기가 경로 오류로 실패하고 검색 백엔드 실행 도구가 확인되지 않아 웹 검색으로 공식 자료를 직접 확인했다. 경쟁 제품을 설치하여 기능·속도를 비교하거나 커뮤니티 수요를 직접 조사하지는 않았다.

## 5. A — 처음 보는 사람이 이해하고 사용할 수 있게 한다

### 5.1 README와 앱의 첫 화면을 같은 이야기로 구성한다

소개는 “ASP.NET Core API의 호출 경로와 코드 근거를 확인하고, AI 코딩 에이전트에 필요한 문맥을 전달하는 로컬 도구다”로 정리한다. 정적 호출 관계이며 실제 요청의 실행 이력·시간을 수집하지 않는다는 설명을 바로 붙인다. TraceLens라는 이름을 런타임 분산 추적으로 오해하지 않도록 한다.

README 첫 화면에는 한 문장 설명, 실제 버전의 60~90초 시연, 빠른 시작, 지원 범위, AI 사용 흐름을 순서대로 둔다. 설치 설명을 읽기 전에 여섯 화면의 모든 기능을 알아야 하는 구조를 줄인다. 기존 한·영 매뉴얼은 상세 설명으로 연결한다.

`client/src/components/WelcomePanel.tsx`와 `GuidedWalkthrough.tsx`를 추가하고 `App.tsx`가 다음 상태를 관리한다.

```text
분석 전 → 예제 선택 또는 내 프로젝트 선택 → 분석 준비 확인
       → 진입점 선택 → 소스 근거 확인 → AI 문맥 복사
```

가이드는 `stepId`, 완료 조건, 대상 UI 요소 ID, 설명 키를 데이터로 정의한다. 좌표에 의존한 안내를 피하고 실제 선택·복사 완료 이벤트로 진행한다. 언제든 닫고 다시 열 수 있게 한다. 기존 최근 경로 복원은 유지하되 예제 상태가 사용자의 최근 프로젝트를 덮어쓰지 않게 한다.

### 5.2 예제는 즉시 탐색과 직접 분석을 구분한다

기존 `Fixtures`와 `FixturesData`를 바탕으로 주문 처리·보상 누락을 설명하는 예제 두 개를 만든다. 배포용 예제에는 출처·예상 분석 결과·학습 순서를 포함한다.

즉시 탐색은 사전 생성한 그래프와 **해당 예제의 소스만** 포함한 샘플 번들을 사용한다. 샘플 어댑터를 통해 기존 화면에 연결하고, 로컬 파일 읽기·에디터 열기·실제 MCP 호출은 예제에서 가능한 범위에 맞게 표시한다. 외부 저장 JSON을 신뢰된 샘플처럼 취급하지 않는다. 직접 분석은 사용자가 고른 폴더에 예제 프로젝트를 복사하고 명시적으로 실행한다.

첫 시연은 “주문 API 선택 → Repository 호출 확인 → 실패 시 보상 누락 확인 → 근거가 포함된 질문 복사”로 구성한다. 외부 AI 계정 없이도 탐색과 문맥 미리보기까지 완료할 수 있게 한다.

### 5.3 UI 국제화와 명칭을 정리한다

`client/src/i18n/ko.ts`, `en.ts`, `I18nProvider.tsx`를 만들고 한국어 사전의 키로 영어 사전 타입을 제한한다. 언어는 앱 설정에 저장하고 기본값은 브라우저 언어를 참고한다. 일반 문구뿐 아니라 `aria-label`, 빈 화면, 오류, 날짜 표시, 질문 템플릿도 언어를 적용한다. 심볼·라우트·코드는 번역하지 않는다.

`Claude에게 질문`은 `AI에게 질문`으로 바꾸고, 실행 방식은 `문맥 복사`, `Claude Code로 실행`, `에디터 열기`처럼 실제 동작을 표시한다. 기존 외부 MCP 연동 안내는 그대로 연결한다. 영어 문서만 보고 시작한 사용자가 버튼 이름을 대응할 수 있어야 한다.

### 완료 기준

- 처음 보는 사용자 5명 중 4명이 예제에서 선택→소스 확인→문맥 복사를 도움 없이 5분 안에 마치는 것을 초기 목표로 삼는다.
- 한국어·영어 모두 키보드로 예제 선택, 진입점 선택, 질문 복사가 가능해야 한다.
- 영어 전환 시 버튼·오류·접근성 라벨에 번역 누락이 없어야 한다. 실제 코드의 한국어 문자열은 누락으로 계산하지 않는다.
- README와 매뉴얼의 명령·시연에 대상 릴리스 버전을 표기한다. 목업 이미지는 실제 화면으로 소개하지 않는다.

## 6. B — 설치와 배포를 제품 기능으로 다룬다

### 6.1 배포 호스트와 명령을 작게 추가한다

새 `src/TraceLens.Cli`에 명령 처리를 두고, Server의 호스트 구성과 Mcp의 호스트 구성을 재사용 가능한 진입 함수로 추출한다. Analyzer는 호스트를 참조하지 않는다. CLI가 `serve`·`analyze`·`mcp` 중 하나를 골라 해당 호스트를 호출한다. 명령 간 실행 상태를 공유하려고 거대한 전역 호스트를 만들 필요는 없다.

아래는 구현 후 제공할 명령 형태의 초안이다. 패키지 ID와 실제 게시 주소는 공개 전에 확정한다.

```text
tracelens doctor --target <solution-or-project-path>
tracelens serve
tracelens analyze <solution-or-project-path>
tracelens mcp --graph <graph-path>
tracelens demo
```

주 배포 후보는 `.NET tool`이며, 초기에는 Windows x64 portable ZIP도 제공한다. 웹 빌드 결과를 패키지에 포함하고 콘텐츠 루트는 실행 파일/패키지 기준으로 고정한다. 대상 프로젝트 폴더에서 실행해도 UI가 열려야 한다. MCP 실행에 필요한 `.deps.json`, `.runtimeconfig.json`, 의존 DLL과 MSBuild 관련 파일이 실제 패키지에 포함되는지 확인한다. 별도 MCP DLL 경로를 조합하는 기존 코드도 패키지 레이아웃에 맞춰 수정한다.

도구 실행 환경과 분석 대상 빌드 환경을 구분한다. self-contained 배포를 하더라도 대상 솔루션 분석에는 적절한 SDK·MSBuild·참조 패키지가 필요할 수 있다. 현재 `net8.0` 타깃만 보고 모든 최신 대상 SDK·운영체제를 지원한다고 선언하지 않는다. `global.json`과 필요한 워크로드를 진단하고 확인한 조합만 지원 표에 적는다.

### 6.2 doctor가 실패 원인과 다음 행동을 알려준다

`EnvironmentDiagnostics`에서 SDK/MSBuild 탐색, 대상 확장자·파일 존재, 분석 결과 저장 권한, 포트 충돌, MCP 호스트 파일 존재, 선택적 CLI 존재를 검사한다. API 키나 전체 환경 변수는 수집하지 않는다. 서버 없이도 실행 가능하게 하며 결과는 `code`, `severity`, `message`, `suggestedAction`으로 반환한다.

초기 오류 코드는 `SDK_NOT_FOUND`, `SDK_MISMATCH`, `TARGET_NOT_FOUND`, `UNSUPPORTED_TARGET_FORMAT`, `OUTPUT_NOT_WRITABLE`, `PORT_IN_USE`, `MCP_HOST_MISSING`으로 충분하다. AI CLI가 없는 것은 분석 기능의 실패로 처리하지 않는다. restore·설치·설정 변경은 doctor가 자동 실행하지 않는다.

`.slnx`는 현재 로더가 허용하지 않으므로 지원 여부를 분명히 표시한다. SDK/MSBuild/Roslyn 조합을 검증한 뒤 `SolutionLoader`와 대상 선택기·CLI의 확장자 허용을 함께 확장한다. 확장자 검사만 풀고 지원 완료라고 하지 않는다.

### 완료 기준

- TraceLens 소스와 Node.js가 없는 환경에서 배포 패키지를 실행하여 UI·소스 보기·MCP 조회가 동작해야 한다. 대상 분석에 필요한 .NET SDK는 준비한다.
- 경로에 공백·한글이 있어도 동작하고, 어떤 작업 디렉터리에서 시작해도 정적 파일을 찾는다.
- 초기 지원 운영체제마다 새 사용자 환경으로 확인한다. 검증 전 macOS/Linux를 지원 완료로 표기하지 않는다.
- 로컬 패키지 생성 스크립트와 체크섬·버전·수동 검증 기록을 남긴다. 패키지 게시·공개 홍보는 별도 실행 작업으로 남긴다.

## 7. C — 지원 범위와 분석의 신뢰성을 먼저 개선한다

### 7.1 Minimal API를 호출 탐색의 진입점으로 포함한다

Minimal API는 람다, 로컬 함수, 메서드 그룹을 핸들러로 사용할 수 있고 라우트 그룹도 제공한다. 등록 구문을 단순 문자열 검색하는 방식으로는 부족하다. [Microsoft 공식 라우트 핸들러 문서](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/minimal-apis/route-handlers?view=aspnetcore-10.0)를 지원 사례의 기준으로 삼는다.

`MinimalApiEntryPointScanner`를 추가하고 기존 Controller 스캐너와 공통 결과로 합친다.

1. Roslyn `IInvocationOperation`의 대상 메서드·어셈블리와 수신 타입으로 ASP.NET Core의 `MapGet`·`MapPost`·`MapPut`·`MapDelete`·`MapPatch`·`MapMethods`를 식별한다. 이름만 같은 사용자 메서드는 제외한다.
2. 라우트는 `SemanticModel.GetConstantValue`로 상수만 확정한다. `MapGroup` 수신 객체를 로컬 변수·메서드 인자 바인딩으로 추적하여 정적 접두사를 합친다.
3. 메서드 그룹은 기존 메서드 심볼로 연결한다. 람다와 로컬 함수는 `CallableDescriptor`로 실행 본문·소스 위치·표시 ID를 제공한다.
4. `ScannedEntryPoint`가 `IMethodSymbol`만 전제하는 구조를 바꾸고, `GraphNodes`, `CallGraphWalker`, `SolutionScanner`가 해당 callable을 처리하도록 함께 수정한다. 진입점 목록만 추가하면 기본 `analysisScope=solution`에서 핸들러 노드가 빠질 수 있으므로 양쪽 모드를 검증한다.
5. `app.MapFeatureEndpoints()`처럼 솔루션 안 확장 메서드에 등록이 숨은 경우 제한 깊이로 본문과 인자 바인딩을 따라간다. 순환 방문을 막고, 제한 초과는 미해석 사유로 기록한다.
6. 동적 문자열·복잡한 분기·외부 패키지의 자체 라우팅 DSL은 미지원/추정으로 남긴다. 지원하지 않는 경우 진입점 0개를 조용히 정상 결과로 끝내지 않는다.

엔드포인트 ID는 핸들러 노드 ID와 분리한다. `projectKey + httpMethod + normalizedRoute + registrationIdentity`를 이용하고 동일 메서드에 여러 라우트가 연결될 수 있게 한다. 의미적 등록 식별자를 우선하고 동일한 등록이 여러 개면 구조적 위치를 보조키로 쓴다. 파일 줄 번호만으로 영구 ID를 만들지 않는다.

### 7.2 호출 근거와 미해석 범위를 보존한다

`InvocationResolver.ResolveCalls`의 반환을 단순 심볼 목록에서 해석 결과 목록으로 확장한다. 결과에는 선언상 대상, 해석된 대상, 호출 위치, `direct`·`diRegistration`·`singleImplementation` 등의 해석 종류와 근거를 담는다.

`SymbolInfo.Symbol`이 없을 때 첫 `CandidateSymbols`를 곧바로 확정 호출로 채택하는 현재 경로는 보수적으로 바꾼다. 후보가 모호하면 `ambiguousSymbol`로 기록하고 확정 엣지에서 제외한다. `DiResolver`도 등록 메서드 이름뿐 아니라 실제 심볼을 검사하며, 조건부 등록·keyed 서비스·복수 구현체를 구분할 수 없으면 확정하지 않는다.

엣지 자체는 기존 `From/To` 중복 제거를 유지한다. 상세 근거는 별도 `CallSite` 목록에 두어 동일 메서드 쌍의 여러 호출 지점을 잃지 않게 한다. UI에서는 엣지 선택 시 실제 호출 줄과 해석 이유를 보여준다. 외부 API와 미해석 호출은 상세의 경계 목록에 표시하며 호출 엣지 종류를 늘리지 않는다.

람다·로컬 함수 본문을 부모 메서드의 `DescendantNodes()`로 모두 수집하면 실제 호출되지 않은 중첩 본문까지 부모의 직접 호출로 보일 수 있다. callable 경계에서 순회를 멈추고, 로컬 함수의 직접 호출은 해당 callable에 연결한다. delegate의 실제 호출 대상을 증명하지 못하면 관계를 추정한다. 이벤트 구독을 새 호출 흐름으로 해석하지 않는다.

### 7.3 분석 품질을 숫자와 이유로 보여준다

`SolutionLoader`의 workspace·컴파일 진단을 `AnalysisDiagnostics`에 수집한다. UI에는 `불러온 프로젝트 / 전체 프로젝트`, `컴파일 오류가 있는 프로젝트`, `확정·추정·미해석 호출 지점`, `설정으로 제외한 범위`, `최대 깊이로 잘린 범위`를 표시한다.

“정확도 95%”는 사용하지 않는다. 대신 `해석률 = 해석한 지원 대상 호출 지점 / 검사한 지원 대상 호출 지점`처럼 분모가 정의된 수치만 쓴다. 해석률과 호출 정확도는 별개다. DB·미들웨어 규칙의 기존 확실도·꺼짐 카탈로그도 문맥 전달까지 보존한다.

### 완료 기준

- Controller와 Minimal API 양쪽에서 고정 라우트·동일 핸들러의 복수 라우트·중첩 그룹·메서드 그룹·람다·로컬 함수의 진입점과 호출 경로를 검증한다.
- 이 저장소 자체의 `Program.cs → Map*Endpoints → HandleAsync` 형태를 회귀 대상으로 삼는다. 분석 산출물은 정해진 대상 폴더에만 생성한다.
- 동적 라우트·복수 DI 구현·컴파일 오류가 있을 때 과장된 확정 연결 대신 명시적 진단이 나와야 한다.
- 호출 위치가 실제 소스와 일치하고, 호출되지 않은 중첩 함수 본문의 호출을 부모의 직접 호출로 표시하지 않아야 한다.

## 8. D — 소스·UI·MCP가 같은 분석을 바라보게 한다

### 8.1 파일 목록과 분석 입력을 스냅샷에 포함한다

`AnalysisManifest`를 만들어 분석한 모든 소스 문서와 프로젝트·설정 입력을 기록한다. 최소 범위는 `.cs`, 대상 `.sln`/`.csproj`, 참조 프로젝트 파일, `tracelens.config.json`, 적용되는 `Directory.Build.props/targets`, `Directory.Packages.props`, `global.json`이다. 실제 MSBuild import와 analyzer/source-generator 입력을 어디까지 기록하는지 명시한다. 추적하지 못한 입력이 있으면 제한을 남긴다.

기록한 파일 해시뿐 아니라 소스 경로 집합을 비교한다. 기존 프로젝트 루트 아래의 새 `.cs`도 파일 목록 검사로 찾고, `bin/obj/.git/.tracelens`와 명시적 제외 경로를 제외한다. 프로젝트 밖에서 링크된 소스는 별도 허용 루트·추적 여부를 기록한다. 확인 범위를 벗어나면 `unknown`으로 표시한다. 이 검사는 파일 목록·해시 비교이며 Roslyn 재분석을 실행하지 않는다.

상태는 `fresh`, `stale`, `unknown`으로 유지하고 추가·수정·삭제·설정 변경 이유를 반환한다. 30초 신선도 확인을 유지하되 동일 스냅샷에 대한 동시 요청은 하나로 합친다. AI에 실제 소스를 반환하는 시점에는 필요한 파일을 다시 검사한다. 최근 검사 결과만으로 소스 일치를 확정하지 않는다.

### 8.2 분석 도중 파일이 바뀌는 경우를 처리한다

그래프를 만든 Roslyn 문서의 원문 체크섬과 디스크 바이트 해시를 구분하여 보존한다. 분석 시작·종료 시 입력 목록과 해시를 검증하고 변경이 있으면 `changedDuringAnalysis`로 결과를 표시한다. 새 분석을 자동 재시도하지 않는다.

`graph.json`은 같은 디렉터리의 임시 파일에 완전히 기록한 다음 검증하고 교체한다. 취소·실패 시 이전 정상 그래프를 유지한다. UI 메모리의 `GraphStore` 교체도 파일 게시가 성공한 뒤 수행한다. 단일 대상의 동시 분석은 직렬화하거나 명시적으로 거절한다.

### 8.3 snapshotId로 UI와 에이전트의 결과를 맞춘다

`snapshotId`는 분석 실행마다 부여하고 입력 해시 묶음인 `inputFingerprint`를 별도로 둔다. Context/API/MCP 응답에 두 값과 분석 시각을 포함한다. 요청에서 기대한 `snapshotId`가 현재 결과와 다르면 `SNAPSHOT_MISMATCH`로 반환한다.

현재 가져오기는 메모리 그래프만 바꾸고 MCP는 대상의 디스크 그래프를 읽을 수 있다. 가져온 파일은 우선 `offlineSnapshot`으로 취급한다. 사용자가 원본 루트를 연결하고 입력 일치를 확인한 뒤 해당 스냅샷의 로컬 보관 경로를 MCP에 전달한다. 활성 `graph.json`을 묵시적으로 덮어쓰지 않는다. 오래된 메서드 줄 범위에 현재 소스를 붙여 “분석 당시 코드”라고 표시하지 않는다.

MCP와 Server에서 공유할 `SourceAccessPolicy`는 정규화된 루트 포함 여부, 허용 소스 목록, 심볼릭 링크·Windows junction의 실제 대상 경로를 검사한다. 가져온 JSON의 `rootDirectory`만으로 로컬 파일 접근 권한을 부여하지 않는다. 조회 범위·응답 바이트 상한도 둔다. 이 조치는 현재 경로 검사가 있는 코드를 제품 배포·가져오기 흐름에 맞춰 보강하는 것이다.

### 완료 기준

- 기존 파일 수정·삭제뿐 아니라 새 소스·설정·프로젝트 참조 변경에서 `fresh`가 남지 않아야 한다.
- 분석 중 저장, 취소, 그래프 교체 중 MCP 읽기에서 부분 JSON을 정상 그래프로 제공하지 않아야 한다.
- UI에서 그래프 B를 가져오고 디스크에 A가 남아 있으면 AI가 A를 조용히 조회하지 않아야 한다.
- 구버전 그래프는 계속 볼 수 있지만 새 신선도 입력이 없으면 `unknown`과 재분석 안내를 표시해야 한다.

## 9. E — AI에 전달할 작업 문맥을 제품의 중심 기능으로 만든다

### 9.1 선택 위치를 작업 문맥으로 확장한다

`ContextBuilder`는 선택 항목, 작업 목적, 길이 제한을 받아 결정적인 규칙으로 문맥을 만든다. 이 단계 자체에는 LLM 호출이 필요하지 않다.

입력 선택은 `node`, `endpoint`, `class`, `finding`, `writePath`, `middlewareStep`을 우선 지원한다. 기존 UI에서 `AskContext`를 만드는 여러 분기 대신 `{ kind, id, snapshotId }`를 서버에 전달한다. 클래스만 선택한 경우에도 관계 요약과 대표 멤버를 만들 수 있게 하여, 실행 가능한 `nodeId`가 없으면 클립보드만 가능한 현재 제약을 완화한다.

문맥에는 다음을 우선순위대로 포함한다.

1. 사용자 작업 목적·질문과 선택한 코드의 식별자를 넣는다.
2. 분석 시각·snapshotId·신선도·분석 범위와 중요한 미해석 사유를 넣는다.
3. 선택한 메서드/핸들러의 시그니처와 검증된 소스 구간을 넣는다.
4. 선택 진입점에서 대상까지의 대표 호출 경로와 각 호출 지점의 근거를 넣는다.
5. 직접 호출자·피호출자와 관련 DB·캐시·미들웨어 점검을 요약한다.
6. 관련 테스트 후보가 확인되는 경우 근거와 함께 제시한다. 테스트를 실행한 결과처럼 표현하지 않는다.
7. 길이 제한으로 생략한 항목과 추가 조회 방법을 넣는다.

기본은 균형 모드로 선택 본문과 제한된 인접 관계를 포함한다. 짧게·균형·자세히 옵션은 우선 문자/바이트·노드 수의 결정적 상한으로 구현한다. 모델별 tokenizer가 없으면 “예상 토큰”임을 표시한다. 문맥 헤더와 누락 사유를 먼저 예약하고, 넘치는 소스는 구간 단위로 줄인다. 선택 본문이 잘렸으면 `truncated=true`와 빠진 줄 범위를 명시한다.

### 9.2 공통 서비스와 응답 계약

`src/TraceLens.Context`를 새 순수 조회 라이브러리로 두어 `GraphIndex`, `ContextBuilder`, `ImpactAnalyzer`, `SnapshotComparer`, 스냅샷 검증·소스 접근의 공통 계약을 둔다. 이 라이브러리는 Analyzer 모델을 참조하고 Server/Mcp를 참조하지 않는다. 양쪽 호스트가 같은 결과를 반환한다는 경계를 먼저 잡는다.

다음은 핵심 DTO의 축약 초안이다. 예시 ID와 경로는 실제 분석 결과가 아니다.

```json
{
  "contextVersion": 1,
  "snapshotId": "example-snapshot-id",
  "inputFingerprint": "sha256:example",
  "selection": { "kind": "node", "id": "Example.OrderService.Create()" },
  "intent": "review-change",
  "freshness": { "status": "fresh", "reasons": [] },
  "summary": "선택한 주문 처리 메서드의 검토 문맥이다.",
  "evidence": [
    {
      "id": "e1",
      "kind": "callSite",
      "file": "Controllers/OrdersController.cs",
      "startLine": 30,
      "endLine": 30,
      "resolution": "diRegistration"
    }
  ],
  "sourceSnippets": [],
  "paths": [],
  "findings": [],
  "limitations": [],
  "truncated": false,
  "omitted": { "nodes": 0, "sourceRanges": [] }
}
```

`POST /api/context`는 구조화 DTO와 같은 DTO에서 생성한 `markdown`을 반환한다. UI·클립보드·인앱 실행·MCP에서 서로 다른 문맥을 조립하지 않는다. 미리보기에는 포함된 파일, 소스 포함 여부, 길이, 제외 항목을 표시한다.

`freshness=stale/unknown`에서도 과거 그래프의 메타데이터 요약은 반환할 수 있다. 다만 오래된 위치 정보와 현재 소스를 섞은 수정용 문맥을 기본으로 반환하지 않는다. 재분석 또는 원본 확인으로 연결한다. 현재 소스를 명시적으로 읽는 기능을 유지한다면 `sourceVersion=current`로 표시하고 분석 스냅샷과 일치 여부가 미확인임을 구분한다.

### 9.3 MCP를 작은 목적별 도구로 확장한다

| 제안 도구 | 주요 입력 | 반환 내용 |
|---|---|---|
| `get_analysis_status` | 기대하는 snapshotId를 선택적으로 지정한다. | 분석 대상·시각·신선도·지원 기능·진단 요약을 반환한다. |
| `get_context` | selection, intent, budget, expectedSnapshotId를 지정한다. | UI 문맥 미리보기와 같은 DTO를 반환한다. |
| `get_entrypoint_flow` | endpointId, depth, maxNodes를 지정한다. | 단일 HTTP 진입점의 제한된 경로와 경계를 반환한다. |
| `get_findings` | endpointId/nodeId, ruleId, limit/cursor를 지정한다. | 기존 DB·미들웨어의 점검 근거와 확실도를 반환한다. |
| `get_impact` | nodeIds, maxDepth, maxNodes를 지정한다. | F에서 구현할 영향 후보와 근거 경로를 반환한다. |
| `compare_snapshots` | baselineId, currentId를 지정한다. | G에서 구현할 구조·본문·점검 차이를 반환한다. |

기존 6개 도구는 유지한다. 검색·목록에는 선택적 `limit/cursor`를 추가하고, 소스 조회에는 상한과 스냅샷 정보를 추가한다. 기존 클라이언트를 깨뜨리는 반환 구조 변경이 필요하면 새 도구 이름이나 명시적 버전을 사용한다.

`GraphFileStore`는 한 호출에서 고정한 스냅샷을 사용한다. 같은 질문의 후속 호출에는 기대 snapshotId를 전달하여 분석이 바뀌면 알 수 있게 한다. 전체 파일 읽기의 반복은 snapshotId 단위의 불변 그래프·인덱스 캐시로 줄인다. 갱신 감지는 파일 메타데이터를 참고하되 실제 읽기·검증 후 ID로 세대를 확정한다.

MCP 도구 설명에 사용하는 상황·한계·자동 재분석을 하지 않는다는 점을 명시한다. JSON Schema로 입출력을 정의하고 `structuredContent`와 같은 내용의 텍스트 표현을 반환한다. 사용 중인 .NET MCP SDK가 실제로 해당 응답을 만드는지 프로토콜 테스트로 확인한다. 속성을 선언한 것만으로 지원 완료라고 판단하지 않는다.

인앱 실행에 새 도구를 연결할 때는 `AskEndpoints`의 허용 도구 목록도 갱신한다. 현재의 6개 도구로 고정된 상태에서는 새로운 문맥 도구를 호출할 수 없다.

### 9.4 에이전트 연동 경험을 정리한다

첫 구현은 문맥 복사와 외부 MCP 연동 안내를 개선한다. Claude Code·Codex CLI의 기존 문서를 활용하고, 대상 프로젝트와 설치된 호스트의 실제 경로를 채운 설정 예시를 생성한다. VS Code도 공식 형식에 맞는 설정 미리보기를 제공한다. 기존 사용자 설정을 묵시적으로 덮어쓰지 않는다.

인앱 실행 대상을 늘릴 때는 `IAgentRunner`로 CLI 의존 부분만 분리한다. 첫 구현은 기존 Claude 호출의 이동으로 제한한다. 여러 CLI의 인자·인증·스트림 형식을 동시에 유지하기보다 공통 MCP의 품질을 먼저 확보한다.

분석은 로컬이어도 외부 AI에 질문하면 해당 설정에 따라 코드·요약이 전송될 수 있다. 실행 전 미리보기에 대상과 전달 문맥을 표시하고, 복사한 문맥에도 소스가 포함되는지 알 수 있게 한다. 비밀값 자동 탐지만으로 안전을 보장하지 않으며 기본 제외와 수동 제외를 제공한다. 소스의 주석·문자열은 근거 데이터로 취급하고 도구 실행 지시로 승격하지 않는다.

### 완료 기준

- 같은 스냅샷·선택·예산에서 UI와 MCP가 같은 근거를 반환하는지 고정 픽스처로 검증한다.
- 노드·클래스·DB 점검 선택에서 문맥을 만들고, 별도 등록하지 않은 AI에도 복사해 활용할 수 있어야 한다.
- 근거 ID를 선택하면 실제 소스로 이동하고, 오래된 그래프에서는 잘못된 위치에 현재 코드를 연결하지 않아야 한다.
- 긴 메서드와 다수 호출자도 상한 안에 담고 생략 내용을 표시해야 한다.
- 안내서의 실제 질문으로 MCP 활용을 확인한다. 도구 목록 조회만으로 연동 성공을 판정하지 않는다.

## 10. F — 변경 전에 영향을 받는 API를 찾는다

### 구현 알고리즘

`GraphIndex`에 `nodeById`, `callersByNodeId`, `calleesByNodeId`, `endpointsByNodeId`, `callSitesByEdge`를 구축한다. 선택한 메서드에서 역방향 BFS를 실행하고 도달한 HTTP 진입점을 영향 후보로 반환한다. 방문 집합으로 순환을 막고 깊이·노드·시간 상한과 취소 토큰을 받는다.

탐색 비용은 도달한 부분 그래프의 노드·엣지 수에 비례한다. 초기에는 진입점마다 대표 최단 경로 하나를 반환하고 모든 경로를 열거하지 않는다. 제한에 도달하면 `truncated`와 이유를 반환한다. 같은 메서드가 여러 라우트를 담당하면 해당 endpointId를 모두 반환한다.

UI는 오른쪽 상세의 “변경 영향”에서 영향받는 API 목록을 보여준다. 하나를 선택하면 기존 호출 흐름으로 이동하고 진입점에서 대상까지의 대표 경로를 강조한다. 여러 진입점을 한 호출 그래프로 펼치는 새 모드는 만들지 않는다.

### 판단 한계를 응답에 포함한다

이 결과는 **분석한 메서드 호출 관계에서 도출한 영향 후보**다. 프로퍼티·DTO 형태 변경, reflection, 외부 호출, 이벤트 구독, 런타임 DI 선택까지 증명하지 않는다. 호출자가 발견되지 않았다고 “삭제해도 안전하다”고 표시하지 않는다.

`analysisScope=entryPoints`나 분석 깊이 제한이 있으면 불완전성을 결과에 전달한다. 클래스·DTO 선택에서는 구현된 메서드 범위의 영향과 아직 지원하지 않는 타입/계약 영향을 구분한다. DI·타입 의존 엣지를 추가하여 호출 그래프의 정의를 바꾸지 않는다.

테스트 후보는 분석에 포함된 테스트 메서드에서의 도달 관계가 있을 때 강한 근거로 삼는다. 이름 일치만 있으면 “이름 기반 후보”로 표시한다. 테스트가 그래프에 없으면 미조사로 표시하며 후보 없음과 테스트 커버리지 충족을 혼동하지 않는다.

### 완료 기준

공유 서비스를 두 Controller와 한 Minimal API가 호출하는 픽스처에서 올바른 진입점과 경로를 반환해야 한다. 순환 호출, 같은 메서드의 여러 라우트, 도달 불가, 상한 도달, 부분 분석도 검증한다. UI는 항상 하나의 진입점을 선택하여 경로를 보는 형태를 유지한다.

## 11. G — AI 수정 후 무엇이 바뀌었는지 확인한다

### 11.1 비교 기준을 명시적으로 저장한다

“변경 전으로 저장”으로 분석 스냅샷을 고정하고, 외부 에이전트에서 수정한 다음 “재분석하고 비교”를 누르는 흐름으로 만든다. 비교 기준은 로컬 `.tracelens/history/<snapshotId>/graph.json`에 저장한다. 대상 루트는 기존 `RootDirectory` 규칙을 따르며 TraceLens 본체 루트와 혼동하지 않는다.

초기에는 사용자가 선택한 기준만 보관한다. 보관 상한에 가까워지면 정리를 안내하고 무제한으로 쌓지 않는다. 분석 실패 시 기준과 이전 정상 결과를 유지한다.

### 11.2 호출 차이와 코드 차이를 구분한다

`SnapshotComparer`는 다음을 계산한다.

- endpointId와 HTTP 동사·라우트의 추가·삭제·변경을 비교한다.
- 메서드의 추가·삭제와 시그니처·본문 변경을 비교한다.
- 호출 엣지의 추가·삭제 및 같은 엣지의 해석 근거·확실도 변화를 비교한다.
- DB·캐시 접근과 점검 결과의 신규·유지·소멸·비교 불가를 비교한다.

기존 파일 단위 `FileHashes`만으로는 본문이 바뀐 메서드를 특정할 수 없다. 분석 때 메서드별 `bodyFingerprint`, `signatureFingerprint`를 추가한다. 본문은 trivia를 제외한 토큰 종류와 텍스트의 열로 해시하여 공백·주석 변경을 구분한다. 다만 이 해시는 의미적 동등성의 증명이 아니다.

비교에는 프로젝트 상대 식별자, 완전한 타입 이름, 메서드 종류, 제네릭 인자 개수, 인자 타입·ref 종류를 포함한 `stableSymbolKey`를 추가한다. 기존 `SymbolNames.GetNodeId`는 프로젝트와 일부 오버로드 차이를 충분히 구분하지 못하므로 사전 키 충돌도 진단한다. 기존 ID는 호환용으로 보존하고 문맥 선택을 모호하지 않은 키로 단계적으로 옮긴다. 충돌이 확인되는 경우 현재 그래프 생성부터 데이터를 덮어쓰지 않도록 우선 처리한다.

이름 변경은 원칙적으로 추가·삭제로 처리한다. 본문·구조 유사성으로 “이름 변경 후보”를 제시할 수 있지만 자동 확정하지 않는다. 람다 식별은 등록 위치·구조에 의존하므로 이동·재배열로 일치 여부를 확인할 수 없으면 비교 불확실성을 표시한다.

### 11.3 비교 전제 조건을 검증한다

같은 대상·설정·분석기 버전·규칙 버전·대상 프레임워크·분석 범위인지 확인한다. 다르면 비교 조건이 다르다고 표시하고, 규칙 비활성화나 프로젝트 로드 실패로 사라진 점검을 “수정 완료”로 보지 않는다. 오래된 schema에 지문이 없으면 가능한 추가·삭제 비교로 제한한다.

구조 비교에는 기준 소스 전체를 저장하지 않아도 된다. 본문의 before/after는 사용자가 명시적으로 보관한 소스나 특정 Git 커밋이 있을 때만 제공한다. Git HEAD를 미커밋 상태의 기준 코드 대신 사용하지 않는다. 원본이 없으면 “본문은 변경되었지만 변경 전 소스는 저장되지 않았다”고 표시한다.

관련 테스트의 제안과 실행 결과도 구분한다. 초기에는 복사 가능한 검증 절차를 제공하고 임의 테스트 명령을 자동 실행하는 기능까지 추가하지 않는다. “차이 없음”은 “안전”이나 “테스트 통과”를 의미하지 않는다.

### 완료 기준

본문만 변경, 공백만 변경, 호출 추가, 라우트 삭제, 규칙을 끈 것에 따른 점검 소멸, 분석 실패에 따른 누락을 각각 검증한다. 수정 전후 점검 개수가 감소했다는 이유만으로 수정 성공을 단정하지 않는다.

## 12. H — 기능 설명을 실무 절차로 연결한다

### 12.1 네 가지 레시피를 앱과 문서에서 공유한다

레시피는 `client/src/content/recipes.ts`의 구조화 데이터로 정의하고 앱 가이드와 한·영 매뉴얼이 같은 절차 ID를 참조하게 한다. 번역 문구는 i18n으로 분리한다.

| 레시피 | 앱에서 하는 행동 | AI에 전달할 구체적 요청 예시 | 확인할 결과 |
|---|---|---|---|
| 처음 보는 API를 이해한다. | 진입점과 대표 호출 경로·소스를 확인한다. | “이 API의 입력부터 저장까지를 근거 ID와 함께 설명한다. 정적으로 확인할 수 없는 처리도 명시한다.”라고 요청한다. | 설명의 사실 주장이 소스와 대응하는지 확인한다. |
| 기능 추가를 계획한다. | 대상 메서드·영향 API를 선택하고 문맥을 만든다. | “기존 책임 분리를 유지하면서 변경 위치, 영향 API, 필요한 테스트를 제안한다.”라고 요청한다. | 변경 위치와 테스트 후보의 근거를 확인한다. |
| DB·캐시 불일치를 조사한다. | 쓰기 경로·보상 처리·점검 근거를 선택한다. | “중간 실패로 남는 갱신을 확인하고, 추정을 구분하여 개선안을 제시한다.”라고 요청한다. | 실제 코드와 실패 경로를 확인한다. |
| AI 수정을 검토한다. | 기준 저장→외부 AI 수정→명시적 재분석→비교를 실행한다. | “이 차이에서 의도하지 않은 경로 변화, 남은 점검, 검증 부족을 확인한다.”라고 요청한다. | 분석 차이와 로컬 테스트 결과를 따로 확인한다. |

질문 템플릿은 선택 항목에 맞는 것만 표시한다. 진단 규칙을 더 늘리기 전에 기존 점검 한 건을 어떻게 판단하고 다시 확인하는지 설명할 수 있게 한다.

### 12.2 공유할 자료의 범위를 줄인다

기존 전체 그래프 JSON 저장은 유지하고 별도 동작으로 “선택 범위 Markdown 보고서”를 추가한다. 선택한 API, 호출 경로, 점검 근거, 분석 시점, 한계만 내보낸다. 그림을 포함한다면 선택 진입점의 그림을 대상으로 하고 새 전체 호출 그래프 모드를 만들지 않는다.

공유용 기본 출력에서는 절대 로컬 경로와 소스 본문을 제외한다. 상대 경로·타입명·테이블명도 업무 정보를 포함할 수 있으므로 미리보기에서 제외할 수 있게 한다. HTML을 추가할 때는 내용을 이스케이프하고 스크립트·외부 폰트 없이 읽을 수 있게 한다. 서버를 외부에 공개하는 공유 방식은 추가하지 않는다.

### 완료 기준

레시피 하나를 예제·영어 UI·실제 프로젝트에서 각각 끝까지 진행한다. 실제 프로젝트 자료를 외부에 전송하지 않아도 검증할 수 있어야 한다. 미리보기와 출력이 일치하고 절대 경로나 선택 외 소스가 섞이지 않는지 확인한다.

## 13. I — 큰 코드베이스의 대기 시간을 개선한다

먼저 SDK/프로젝트 로드, 호출 분석, DB·미들웨어 분석, JSON 생성, 초기 화면 표시, 선택·확장, MCP 조회의 시간과 최대 메모리를 측정한다. 병목에 따라 다음을 적용한다.

1. 큰 MCP 응답에 페이지 구분과 문맥 상한을 적용하고 그래프 인덱스를 재사용한다.
2. 진입점·클래스 목록을 가상화하고 기존 네임스페이스 필터·멤버 접기를 유지한다.
3. 배치 계산이 메인 스레드를 막으면 기존 `graph/`의 순수 함수를 Web Worker로 옮긴다.
4. 분석 시간이 길면 진행 상태를 제공하는 작업으로 바꾼다. 로드·스캔·규칙·저장 단계와 실제 처리 건수를 보여주고 근거 없는 진행률을 만들지 않는다.

작업 방식으로 전환할 때 기존 `POST /api/analyze`는 호환 경로로 유지한다. 새 `POST /api/analysis-jobs`는 202와 jobId를 반환하고, `GET /api/analysis-jobs/{id}/events`는 SSE 진행 상태를 반환한다. `DELETE /api/analysis-jobs/{id}`는 취소 요청을 전달한다. 취소가 완료될 때까지 기존 그래프를 유지하고, 새 분석으로의 전환은 완료 알림을 받은 `App.tsx`에서 한 번만 수행한다.

차등 분석과 파일 watch는 이 개선에 포함하지 않는다. 명시적 전체 분석의 속도·표시부터 개선한다. 분석 자체의 시간이 문제인지 문맥 생성·화면 표시 시간이 문제인지 분리해서 판단한다.

### 14.2 schema v6에서 단계적으로 확장한다

다음 schema는 v7을 후보로 삼고 C·D에 필요한 `endpointId`, `snapshotId`, `analysisManifest`, `diagnostics`, `callSites`를 도입한다. 메서드 지문과 안정 키는 G 구현 시 후속 schema로 추가하되, 실제 키 충돌이 발견되면 해당 해결을 앞당긴다. 미래 항목을 모두 선행 구현하지 않고 릴리스마다 구현한 계약만 확정한다.

Analyzer의 C# 모델, Server 응답, client 타입·읽기 처리를 함께 갱신하고 MCP 입출력도 맞춘다. `docs/data-contract.md`에 버전·기본값·이행 규칙·최소 예제를 둔다. 현재 없는 `task.md`를 다시 만들 필요는 없다.

이전 그래프에 없는 정보는 `unknown` 또는 미제공으로 취급한다. 존재하지 않는 호출 근거·본문 지문을 추정으로 채우지 않는다. 과거 endpointId는 라우트·HTTP 동사·nodeId로 읽을 때만 호환 생성하며, 이미 유실된 복수 라우트를 복원한 것처럼 표시하지 않는다. 지원하지 않는 미래 schema는 명시적으로 거절한다. 잘못된 배열·중복 ID·존재하지 않는 노드를 참조하는 엣지·잘못된 경로도 검사한다.

### 14.3 최소 API 계약

| 엔드포인트 초안 | 처리 | 주요 실패·제한 |
|---|---|---|
| `GET /api/diagnostics` | 환경과 현재 분석 능력을 반환한다. | 비밀값을 반환하거나 설치를 실행하지 않는다. |
| `POST /api/context` | 선택과 목적에서 문맥 DTO·Markdown을 생성한다. | 잘못된 선택은 400, 분석 미선택은 404, 스냅샷 불일치는 409로 반환한다. |
| `POST /api/impact` | 여러 nodeId의 영향 후보를 조회한다. | 노드·깊이 상한과 중단 이유를 반환한다. |
| `POST /api/snapshots` | 현재 분석을 명시적으로 기준 저장한다. | 검증한 현재 대상의 저장 위치로 제한한다. |
| `POST /api/snapshots/compare` | 저장된 ID 두 개를 비교한다. | 임의 경로를 받지 않고 비교 조건 불일치를 표시한다. |

새 API 오류는 `{ code, message, details }`로 통일한다. 과거 API는 호환 필드를 유지하며 옮긴다. 오류 code로 UI 번역을 지원하고 MCP도 같은 의미의 code를 반환한다.

## 15. 구현 순서와 공개 판정

### 첫 번째 공개 — 도구를 이해하고 바로 사용한다

A의 README·앱 안내·예제·영어화를 구현하고 B의 배포 시제품을 만든다. C가 끝나기 전에는 Controller 중심의 지원 범위를 명시한다. 처음 보는 사람이 설치에서 막히는지, 분석 대상 선택에서 막히는지, 어디를 봐야 할지 모르는지 관찰한다.

공개 조건은 배포물 단독 실행, 예제 완주, 문서와 실제 화면의 일치다. 기존 MIT LICENSE를 유지하고 이용 시작에 새 회원가입을 요구하지 않는다.

### 두 번째 공개 — 자신의 API 분석 결과를 믿고 활용한다

C·D를 구현한다. Minimal API, 복수 라우트, 분석 누락 표시, 스냅샷과 현재 소스 검증을 먼저 확보한다. schema 이행·이전 저장 파일·MCP 일관성이 검증되기 전에 변경 영향과 수정 안전성을 과장하여 소개하지 않는다.

### 세 번째 공개 — AI에 유용한 문맥을 전달한다

E와 기본 레시피를 구현한다. 기존 외부 CLI 연동으로 실제 작업을 완료하고 수동으로 파일 위치를 붙이는 경우와 비교한다. 추가한 도구 수보다 AI 답변에 정확한 근거가 들어갔는지 판정한다.

### 네 번째 공개 — 수정 영향과 결과를 확인한다

F·G·H를 구현한다. 메서드 변경부터 지원하고 타입·DTO 계약 전체의 파괴적 변경 분석까지 동시에 약속하지 않는다. I는 앞선 공개에서 측정한 병목에 따라 적용한다.

코드 검증은 로컬 `dotnet build`, 관련 `dotnet test`, `client`에서의 `npm test`·`npm run build`를 기반으로 한다. UI는 브라우저, 패키지는 별도 환경, MCP는 실제 프로토콜로 검증한다. 변경에 필요한 검증을 선택하고 CI 작업은 수행하지 않는다.

## 16. 이용자를 늘리는 실행 계획과 효과 측정

### 16.1 널리 소개하기 전에 소수 이용자의 작업을 관찰한다

Controller 중심·Minimal API 중심·독자 DI/DB 래퍼를 사용하는 개발자를 각 몇 명씩, 총 5~10명 모집하는 계획을 세운다. 이는 앞으로 진행할 사용자 조사이며 이번에 이미 실시한 것이 아니다.

동의를 받아 설치, 첫 분석, 임의 API 설명, AI 문맥 전달, 재분석을 관찰한다. 코드를 제공받지 않고도 시간·조작의 어려움·오류 code·지원 패턴을 기록할 수 있게 한다. 발견한 실패는 최소 재현 픽스처로 돌려준다.

### 16.2 소개 자료를 작업별로 만든다

README·매뉴얼을 바탕으로 짧은 화면 녹화와 실제 활용 글 세 개를 준비한다. 주제는 “모르는 API의 경로 찾기”, “공유 서비스 변경의 영향 API 확인”, “AI 수정 뒤 DB 보상 처리 확인”으로 삼는다. 기능 목록보다 시작할 때의 문제와 결과를 보여준다.

공개 후보 채널은 .NET/C# 커뮤니티와 평소 사용하는 AI 코딩 커뮤니티로 잡는다. 이번 문서 작성에서 공개 게시·사용자 연락·Issue 등록은 수행하지 않았다. 실행 가능한 배포물, 지원 표, 실패 시 안내를 먼저 준비한다.

기존 MIT LICENSE에 더해 짧은 `CONTRIBUTING.md`와 수동 갱신하는 릴리스 노트를 준비한다. 분석 누락 보고에는 도구 버전·SDK·대상 형식·최소 코드·기대한 호출·실제 결과를 받는다. 초기 기여 항목은 번역, 익명화한 최소 픽스처, 사용 절차 개선으로 좁힌다.

### 16.3 다운로드 수만으로 성공을 판단하지 않는다

아래 수치는 초기 목표이며 실제 측정 결과가 아니다. 사용자 관찰 후 조정한다.

| 지표 | 정의 | 초기 목표 |
|---|---|---|

AI 활용 비교는 같은 모델·설정과 비슷한 문맥 접근 조건에서 “기존 위치 복사”와 “TraceLens 문맥”을 비교한다. 작업 순서를 바꾸고 정답률·근거·놓친 영향·시간·전달 문량을 측정한다. 소수 성공 사례만으로 보편적 속도 향상을 단정하지 않는다.

## 18. 지금은 늘리지 않을 기능

자동 저장 감지에 따른 재분석, 원격 분석 서버, 이벤트 구독을 포함하는 전체 호출 그래프, 자체 IDE·코드 편집·자동 커밋, 모든 언어 지원, 자동 PR 검토 게시, 대규모 벡터 검색 기반은 이번 권고 범위에 포함하지 않는다.

EF Core와 모든 사내 DB 래퍼를 포괄하는 분석, MediatR 등의 동적 디스패치 해석, 완전한 계약 파괴 검출은 사용자 실패 사례와 기존 설계의 정합성을 확인한 다음 별도로 설계한다. 특히 메시지 핸들러 연결은 현재 호출 엣지 제약과 관련되므로 추측으로 추가하지 않는다.

먼저 제공할 가치는 **예제로 이해하고, 자신의 API를 근거와 함께 탐색하고, AI에 필요한 문맥을 전달하고, 변경 결과를 확인하는 경험**이다. 각 공개의 완료 조건을 이 흐름에 맞춘다.
