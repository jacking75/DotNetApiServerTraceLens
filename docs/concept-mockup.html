CONCEPT MOCKUP v2 · 결정사항 반영

TraceLens ASP.NET Core 코드 흐름을 그래프로 탐색하고, 클릭 한 번으로 Claude Code에게 그 위치를 물어보는 도구

요청하신 두 가지 — ① 코드 흐름을 따라가는 그래프에서 노드를 클릭하면 실제 코드로 드릴다운되는 탐색 UI, ② 선택한 지점의 정확한 위치(파일·라인·심볼)를 캡처해서 Claude Code에게 바로 물어볼 수 있는 연동 — 을 하나의 화면 개념으로 합쳐서 목업으로 만들었습니다. 아래 데모는 실제 분석 결과가 아니라 손으로 채운 가짜 데이터이며, 그래프 노드를 클릭해보면서 동작 흐름을 먼저 감으로 잡아본 뒤, 그 아래에서 아키텍처와 구현 방식에 대한 설명을 읽는 순서를 권장합니다. 이번 버전에는 그래프 규모·엣지 범위·최신성 표시·MCP 보안·개발 순서에 대해 정리해주신 방향을 반영했고, 6번과 7번 섹션에 정리했습니다.

1 인터랙티브 목업 — 직접 클릭해보기

왼쪽은 OrdersController → OrderService → OrderRepository → DbContext로 이어지는 요청 처리 흐름 그래프입니다. 노드를 클릭하면 오른쪽에 해당 위치의 코드가 뜨고, 그 아래 "Claude Code에게 물어보기" 패널에 파일/라인/심볼 정보가 자동으로 채워집니다. OrderService 노드 오른쪽 위의 ⤵ 버튼을 누르면 그 메서드 내부 호출 흐름으로 한 단계 더 들어갑니다.

Level 1 · 요청 흐름 (OrdersController.CreateOrder)
✓ 최신 상태 · 방금 분석
Controller Service Validator Repository DB / Infra
⤵ 버튼 = 내부 흐름으로 드릴다운

2 구성 요소 — 어떤 부품으로 만들어질까

그래프 자체는 예쁜 그림이 아니라, 실제 코드의 구조 정보와 정확히 매핑된 데이터입니다. 그러려면 네 개 정도의 독립적인 조각이 필요합니다.

① Analyzer

Roslyn 기반 정적 분석기

Microsoft.CodeAnalysis(Roslyn)로 솔루션을 파싱해서 컨트롤러/서비스/리포지토리 등 타입과 메서드, 그리고 그것들의 실제 파일 경로·라인 번호를 추출합니다. 엣지는 메서드 호출 관계로만 한정합니다.

  • 메서드 호출 관계(Call Graph) — DI·이벤트 기반 흐름은 엣지에 포함하지 않음
  • 단, Program.cs의 DI 등록(AddScoped 등)은 "인터페이스 → 실제 구현체"를 찾는 용도로만 참고 (예: IOrderService 호출을 실제 OrderService.CreateOrderAsync 노드로 정확히 연결)
  • Controller 액션 → HTTP 라우트 매핑
② Graph Server

그래프 · 소스 서빙 API

Analyzer가 만든 노드/엣지 JSON을 프론트엔드에 서빙하고, 노드 클릭 시 해당 파일의 원본 코드를 라인 단위로 돌려주는 API입니다.

  • ASP.NET Core Minimal API로 만들면 자기 자신을 분석 대상으로 쓰는 것도 가능
  • 자동 재분석은 하지 않고, "다시 분석" 요청이 올 때만 증분 재분석 수행
  • 분석 시점의 파일 해시/타임스탬프를 저장해두고, 현재 디렉토리와 비교해서 최신 여부를 알려줌
③ Web Frontend

그래프 뷰 + 코드 뷰

노드-엣지 그래프 렌더링과 코드 프리뷰 패널을 가진 웹 UI입니다. 데모의 좌/우 2분할 레이아웃이 이 부분의 초안입니다.

  • 그래프: Cytoscape.js / React Flow 같은 라이브러리
  • 코드 뷰: Monaco Editor(읽기 전용) 또는 Shiki로 하이라이팅
④ Claude Code Bridge

선택 위치 → 에이전트 연동

사용자가 그래프에서 고른 "정확한 위치"를 Claude Code가 이해할 수 있는 형태로 넘겨주는 다리 역할입니다. 아래 3번 섹션에서 옵션을 비교합니다.

3 전체 동작 흐름

한 번의 "분석 → 탐색 → 질문"이 실제로는 이런 순서로 일어난다고 그려봤습니다.

솔루션 인덱싱

개발자가 분석할 .sln 경로를 지정하고 최초 1회 전체 분석을 실행합니다. 이후에는 자동이 아니라, 사용자가 "다시 분석" 버튼을 눌렀을 때만 변경된 부분을 증분 분석합니다.

그래프 데이터 생성

Roslyn 분석기가 HTTP 진입점(컨트롤러 액션)부터 시작해서 호출 체인을 따라가며 노드(타입/메서드)와 엣지(메서드 호출 관계), 각 노드의 파일·라인 정보를 JSON으로 만듭니다. 이때 분석 시점의 코드 스냅샷 정보도 함께 저장합니다.

그래프 탐색

사용자는 HTTP 엔드포인트 같은 진입점부터 시작해서, 실제 요청이 흘러가는 순서대로 그래프를 따라가며 전체 구조를 파악합니다. 전체 그래프를 한 번에 그리지 않고, 항상 진입점 기준 단계식으로 필요한 만큼만 펼칩니다.

드릴다운

궁금한 노드를 클릭하면 그 노드의 실제 소스 코드가 옆 패널에 뜨고, ⤵ 버튼으로 그 메서드 "내부"의 더 세부적인 호출 흐름으로 들어갈 수 있습니다.

위치 캡처

노드를 선택한 상태 = 파일 경로 + 라인 범위 + 심볼명(예: OrderService.CreateOrderAsync(CreateOrderRequest))이 자동으로 확정된 상태입니다. 사용자가 따로 경로를 찾아 붙여넣을 필요가 없습니다.

Claude Code에 질의

캡처된 위치 정보 + 사용자의 질문이 선택한 연동 방식(클립보드/MCP/에디터)에 따라 Claude Code로 전달되고, 답변을 UI 안에서 바로 확인합니다.

4 "정확한 위치를 에이전트에게 넘기는" 세 가지 방식

데모의 우측 상단 토글이 바로 이 세 가지입니다. 로컬 환경에서만 동작하는 것을 전제로, 난이도가 낮은 클립보드 복사부터 구현해서 먼저 실제로 쓰기 시작하고, 이후 MCP 직접 연동으로 넓혀가는 순서를 제안합니다. 자세한 순서는 7번 섹션에 정리했습니다.

방식 동작 장점 단점
클립보드 복사 "파일 경로 + 라인 범위 + 심볼명 + 질문"을 정형화된 텍스트로 만들어 클립보드에 복사. 사용자가 이미 열려 있는 Claude Code 터미널에 붙여넣기. 서버 쪽 추가 연동 작업이 거의 없음. 어떤 환경에서도 동작. 붙여넣기라는 수동 단계가 남음. "클릭 한 번"의 느낌은 덜함.
MCP 직접 연동 Analyzer/Graph Server를 MCP 서버로도 노출해서, Claude Code가 get_symbol_source 같은 도구로 직접 위치를 조회하거나, 반대로 UI가 실행 중인 Claude Code 세션에 메시지를 흘려보냄. 정말로 "클릭 → 바로 질문"이 됨. 그래프가 곧 에이전트의 컨텍스트 소스가 됨. 세션 연결(로컬 소켓/파일 기반 등)을 직접 설계해야 함. 구현 난이도가 가장 높음.
에디터에서 열기 클릭 시 VS Code 등 이미 Claude Code 확장이 떠 있는 에디터에서 해당 파일·라인을 열어줌(예: vscode://file/...:line). 질문은 에디터 안의 Claude Code UI에서 이어감. Claude Code와의 대화 UI를 따로 만들 필요가 없음. 구현이 상대적으로 쉬움. 그래프 웹앱과 에디터를 오가야 해서, 그래프 화면 안에서 답변까지 보는 몰입감은 떨어짐.

5 기술 스택 후보

분석기

Roslyn 위에서 시작

맨땅에서 만들기보다, 이미 존재하는 Roslyn 기반 Call Graph 프로젝트(csharp-call-graph, RoslynCallGraph, dependator 등)의 분석 로직을 참고해서 ASP.NET Core 패턴(Controller/DI/미들웨어)에 맞게 확장하는 편이 빠릅니다.

그래프 렌더링

Cytoscape.js / React Flow

계층형(top-down) 레이아웃과 확대/축소, 서브그래프 펼치기를 기본 지원해서 이번 데모 같은 드릴다운 UX를 구현하기에 적합합니다.

코드 표시

Monaco Editor

VS Code와 같은 엔진이라 C# 문법 하이라이팅, 특정 라인 강조, 미니맵까지 그대로 활용할 수 있습니다.

에이전트 연동

Claude Agent SDK / MCP

Graph Server를 MCP 서버로 겸용하거나, Claude Agent SDK의 headless 모드로 질문을 보내고 스트리밍 응답을 UI에 그대로 표시하는 방식을 검토할 수 있습니다.

6 결정된 설계 원칙

지난 다섯 가지 고민에 대해 다음과 같이 방향을 정했습니다. 위 데모와 아키텍처 설명은 이 방향을 반영해서 업데이트했습니다.

  • 그래프 규모 → 진입점 기준 단계식. 전체 그래프를 한 번에 그리지 않고, 항상 HTTP 진입점에서 시작해서 필요한 만큼만 드릴다운으로 펼칩니다. 데모의 Level 1 → Level 2 전환이 이 방식의 구현입니다.
  • 엣지 범위 → 메서드 호출 중심. DI 의존 관계나 이벤트/메시지 흐름은 엣지로 그리지 않습니다. DI 등록 정보는 "인터페이스가 실제 어떤 구현체로 연결되는지" 찾아서 정확한 호출 대상 노드를 그리는 데만 내부적으로 사용합니다.
  • 최신 상태 유지 → 수동 갱신 + 신선도 표시. 파일 저장 시 자동 재분석은 하지 않습니다. 대신 마지막 분석 시점의 코드 스냅샷을 저장해두고, 현재 디렉토리의 코드와 같은지를 항상 화면에 표시해서 "오래된 그래프를 보고 있다"는 걸 놓치지 않게 합니다. 데모 상단의 신선도 배지와 "다시 분석" 버튼이 이 부분입니다. (우측 상단의 "코드가 바뀌었다고 가정해보기"를 눌러보면 변경 감지 상태가 어떻게 보이는지 확인할 수 있습니다.)
  • MCP 보안 → 로컬 전용. 그래프 서버와 MCP 연동은 원격으로 노출하지 않고, 같은 머신 안에서만 동작하는 것을 기본값으로 합니다.
  • 개발 순서 → 단계적으로, 목표는 실전 사용. "임시로 써보는 시제품"이 아니라 처음부터 실제로 계속 쓸 도구를 목표로 하되, 한 번에 다 만들지 않고 큰 틀을 먼저 세운 뒤 핵심 기능을 하나씩 채워나갑니다. 구체적인 순서는 아래 7번 섹션에 정리했습니다.

7 단계별 개발 순서

각 단계가 끝날 때마다 "실제로 켜놓고 쓸 수 있는 상태"가 되는 것을 기준으로 순서를 나눠봤습니다.

큰 틀 세우기

Roslyn으로 메서드 호출 관계를 추출하고, 진입점 기준 그래프(Level 1)와 드릴다운(Level 2), 코드 패널, 클립보드 복사까지 붙입니다. 이 상태만으로도 팀 안에서 코드 흐름을 설명하는 용도로 실제로 쓸 수 있습니다.

신뢰성 채우기

"다시 분석" 버튼, 마지막 분석 시점 저장, 현재 코드와의 신선도 비교 표시를 추가합니다. 이 단계부터 "지금 보고 있는 그래프가 실제 코드와 같다"는 걸 확신할 수 있게 됩니다.

에이전트 연동 넓히기

로컬 전용 MCP 서버를 붙여서 그래프에서 선택한 위치를 Claude Code에게 바로 물어볼 수 있게 합니다. 클립보드 복사 방식은 그대로 대안으로 남겨둡니다.

필요해지면 그때 확장

실제로 써보면서 DI·이벤트 흐름까지 엣지에 포함해야 할지, 여러 명이 함께 보는 공유 화면이 필요한지 등은 이 시점에 다시 판단합니다. 처음부터 범위에 넣지 않습니다.

이 문서는 구현 여부를 결정하기 전 아이디어를 눈으로 확인해보기 위한 컨셉 목업입니다. 그래프 데이터와 코드, Claude 응답은 모두 가짜 예시이며 실제 분석 결과가 아닙니다.
