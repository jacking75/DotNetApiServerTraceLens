설계 메모 — 확정 전에 맞출 것

위 화면은 다섯 번째 보기 “DB 접근”의 목업이다. 기존 네 보기가 “코드가 서로를 어떻게 부르는가”를 본다면, 이 보기는 “그 호출이 결국 어느 DB의 어느 테이블을 어떤 키로 건드리는가”를 본다. 분석 대상 코드베이스는 유저 데이터가 userNo 기준으로 8개 샤드에 흩어져 있고, 계정·상점 같은 공통 데이터는 글로벌 DB에 있는 전형적인 게임 서버 형태를 가정했다.

1. 이 보기가 답하는 질문

  • 이 API 하나가 몇 개의 DB·몇 개의 커넥션을 여는가
  • 샤드를 고른 키가 어디서 온 값인가(토큰 / 요청 본문 / 다른 유저의 번호)
  • 고른 샤드와 실제 쿼리 파라미터의 유저가 같은가 — 남의 샤드를 건드리는 코드가 있는가
  • 한 트랜잭션이 두 개 이상의 커넥션에 걸쳐 있는가(샤드 DB + 로그 DB 등)
  • 이 테이블을 바꾸면 어느 코드가 영향을 받는가(테이블 → 코드 역인덱스)

2. 화면 구성

  • 샤드 라우팅 — 진입점 하나를 골라 “요청 → 샤드 키 결정 → 커넥션 획득 → 쿼리 실행”을 단계로 세운다. 문제 지점만 색이 붙는다.
  • 접근 지도 — 클래스 × 테이블 매트릭스. R/W/RW와 데이터소스가 한눈에 보이고, 규칙에 걸린 칸에 테두리가 생긴다.
  • 트랜잭션 — 트랜잭션 경계 안에서 실행된 것들을 순서대로. 걸친 커넥션 수와 외부 호출(HTTP·Redis) 포함 여부가 핵심.
  • 점검 결과 — 규칙에 걸린 항목 표. 심각도·확실도·무시 여부로 거른다.

3. 판정의 근거를 항상 같이 보여준다

“이건 잘못됐다”만 띄우는 도구는 두 번째부터 안 믿게 된다. 그래서 우측 상세에는 항상 샤드 키 출처 체인(어느 파라미터가 어디서 흘러와 어떤 함수로 샤드를 골랐는지)과 그 판단이 확실(대입을 끝까지 따라감)인지 추정(중간에 인터페이스·리플렉션으로 끊김)인지를 같이 적는다.

추정 항목은 기본 접힘으로 두고, “확실한 것만 보기” 토글로 소음을 줄인다.

4. 오탐을 관리하는 장치

  • 랭킹처럼 일부러 전 샤드를 도는 코드가 있다. 항목마다 “의도된 것으로 표시”를 두고 결과를 .tracelens/db-baseline.json에 남긴다.
  • 무시한 항목은 사라지지 않고 회색으로 남아, 나중에 코드가 바뀌면 다시 뜬다(라인 대신 심볼 기준으로 기억한다).
  • 규칙 단위 끄기도 둔다 — 팀이 안 지키기로 한 규칙은 통째로 끈다.

5. 점검 규칙 초안 — 무엇을 어디까지 정적으로 잡을 수 있나

아래가 목업에 넣은 규칙 목록이다. “정적으로 확실”은 Roslyn 심볼·데이터 흐름만으로 판정 가능한 것, “추정”은 값이 런타임에 정해져서 힌트만 줄 수 있는 것이다. 추정 규칙은 결과에 확실도를 반드시 표시한다.

6. 사내 DB 계층을 알려주는 설정 — 이게 없으면 아무것도 못 잡는다

“샤드를 고르는 함수”가 무엇인지는 프레임워크마다 다르다. Dapper·EF Core·자체 래퍼 중 무엇을 쓰는지, 커넥션을 어떤 팩토리로 여는지를 tracelens.config.json에 한 번 적어두면, 그다음부터는 자동으로 따라간다. 자동 인식이 실패하면 “DB 접근 지점을 하나도 못 찾았다”가 아니라 “이 설정을 채워라”를 화면에 띄운다. 

"db": {
  "connectionFactories": [
    "GameServer.Data.IShardConnectionFactory.OpenAsync(int userNo)",   // 첫 인자가 샤드 키
    "GameServer.Data.IGlobalConnectionFactory.OpenAsync()"
  ],
  "shardKeyParameters": ["userNo", "uid", "playerNo"],
  "queryApis": [
    "Dapper.SqlMapper.*",                       // Query/Execute/QueryFirst...
    "GameServer.Data.DbExtensions.ExecProcAsync"
  ],
  "storedProcedurePrefix": "usp_",
  "dataSources": {
    "GameDb":        { "kind": "shard", "shardCount": 8, "shardBy": "userNo % 8" },
    "GameDbReplica": { "kind": "shard", "shardCount": 8, "readOnly": true },
    "GlobalDb":      { "kind": "single" },
    "LogDb":         { "kind": "single", "writeOnly": true }
  },
  "schemaFiles": ["db/schema/*.sql"]            // 있으면 컬럼·인덱스까지 대조
}

7. 기존 보기와의 연결

  • 호출 흐름 / 전체 흐름도 — DB에 닿는 메서드 노드에 데이터소스 색 배지(S3 G)를 단다. 진입점 목록에도 “이 API가 여는 커넥션 수”를 붙인다.
  • 클래스 다이어그램 — 리포지터리 박스에 다루는 테이블 수를 표시하고, 관계 토글에 “DB 접근”을 하나 더 둔다(기본 꺼짐).
  • 시작 흐름 — DbContext·커넥션 팩토리의 수명(Scoped/Singleton) 등록을 이미 보고 있으므로, CONN-002(Singleton 등록) 판정을 여기서 그대로 가져온다.

8. 규모 제약(CLAUDE.md 1번)과의 관계

접근 지도는 클래스 다이어그램과 같은 “전체를 그리는” 화면이라 밀도 손잡이가 필요하다. 데이터소스 필터 · 테이블 검색 · “쓰기만 보기” · “규칙에 걸린 것만 보기” 네 가지를 손잡이로 둔다. 테이블이 200개를 넘으면 처음부터 쓰기만 + 규칙에 걸린 것만으로 켠다.

확인이 필요한 것

  • DB 접근 방식이 무엇인가 — Dapper인가, EF Core인가, 자체 래퍼인가, 저장 프로시저 위주인가? 인라인 SQL이면 문자열 상수를 파싱해 테이블을 뽑을 수 있지만, 프로시저 이름만 있으면 테이블 매트릭스는 프로시저 매트릭스가 된다.
  • 샤드를 고르는 코드가 어떤 모양인가 — factory.Open(userNo)처럼 인자로 넘기나, 미들웨어에서 AsyncLocal/컨텍스트에 담아두고 리포지터리가 꺼내 쓰나? 후자면 흐름 추적이 한 단계 더 필요하다.
  • 샤드 규칙이 userNo % N인가, 매핑 테이블 조회인가? 매핑 테이블이면 “어느 샤드”는 못 정하고 “샤드 키가 무엇인지”까지만 본다.
  • DDL(schema.sql)에 접근 가능한가? 있으면 컬럼 오타·인덱스 없는 조건까지 잡고, 없으면 IDX-* 규칙군은 빼야 한다.
  • 가장 아픈 사고가 무엇이었나 — 남의 샤드 접근인가, 커넥션 누수인가, N+1인가? 규칙 우선순위를 그 순서로 만든다.
