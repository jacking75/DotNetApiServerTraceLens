설계 메모 — 확정 전에 맞출 것

다섯 번째 보기 “DB · 캐시”의 목업이다. 기존 네 보기가 “코드가 서로를 어떻게 부르는가”를 본다면, 이 보기는 “그 호출이 결국 어느 저장소의 무엇을 어떤 순서로 바꾸는가, 중간에 실패하면 무엇이 남는가”를 본다. 샤딩은 선택이다 — 상단 구성 칩을 눌러 “샤딩 8” ↔ “단일 DB”를 바꿔 보면 같은 코드베이스가 두 구성에서 어떻게 다르게 보이는지 확인할 수 있다(샤딩을 안 쓰면 SHARD 규칙군이 통째로 꺼진다).

1. 이 보기가 답하는 질문

  • 이 API 하나가 어느 저장소를 몇 번, 어떤 순서로 건드리는가(DB · 캐시 · 로그)
  • 트랜잭션으로 묶이지 않은 쓰기가 있는가, 중간에 실패하면 무엇이 남는가
  • 남는 것을 되돌리는 코드가 실제로 있는가 — 예외 경로뿐 아니라 조기 반환 경로까지
  • 캐시와 DB가 어긋날 수 있는 자리가 어디인가(무효화 누락, 캐시 먼저 갱신)
  • (샤딩을 쓴다면) 샤드를 고른 키가 어디서 왔고, 쿼리 대상 유저와 같은가

2. 화면 구성 — 하위 보기 5개

  • 실행 경로 — 진입점 하나를 골라 “요청 → (샤드 키) → 커넥션 → 트랜잭션 → 저장소 접근”을 순서대로 세운다.
  • 접근 지도 — 클래스 × 테이블 R/W 매트릭스와, 그 아래 Redis 키 패턴 × 클래스 매트릭스.
  • 트랜잭션 — 경계 안 실행 순서, 걸친 커넥션 수, 외부 호출·Redis 포함 여부.
  • 보상 처리 — 트랜잭션 없이 쓰는 경로마다 “어디서 실패하면 무엇이 남는가”를 격자로 편다.
  • 점검 결과 — 규칙에 걸린 항목 표. 심각도·확실도·무시 여부로 거른다.

3. 보상 처리 점검 — 이번 핵심

트랜잭션이 없으면 “k번째에서 실패했을 때 1..k-1을 사람이 되돌려야 한다”가 된다. 도구는 이렇게 본다:

  • 경로 안의 상태를 바꾸는 단계를 순서대로 뽑는다(DB 쓰기 · Redis 쓰기 · 외부 호출).
  • 실패 처리 경로(catch, if (!ok) return, finally) 안에서 각 단계의 역연산을 찾는다 — INSERT↔DELETE, +N↔-N, SET↔DEL.
  • 단계마다 되돌림 있음 / 없음 / 불필요(재실행 안전) / 불가(외부 발송)로 표시한다.
  • 그 결과를 실패 지점 × 단계 격자로 편다. 빨간 칸이 “그대로 남는 것”이다.

예외 경로만 보는 도구는 return false 같은 조기 반환을 놓친다. 그 자리를 따로 규칙(COMP-006)으로 뒀다.

4. Redis를 저장소로 같이 본다

  • 키를 패턴으로 정규화한다 — user:100342:inv → user:{userNo}:inv. 문자열 보간·결합을 따라가 만든다.
  • 같은 패턴을 누가 쓰고 누가 읽는지 이어서, DB 쓰기 뒤 무효화가 빠진 자리를 찾는다(CACHE-001).
  • TTL 없는 SET, KEYS·FLUSHALL, 반복문 안 GET, 락 해제 누락을 규칙으로 잡는다.
  • 캐시를 먼저 갱신하고 DB가 실패하는 순서는 보상 처리와 같은 문제라 두 보기에서 함께 뜬다(CACHE-002).

5. 샤딩은 설정으로 켠다

dataSources에서 "kind": "shard"로 잡은 데이터소스가 하나라도 있을 때만 SHARD 규칙군이 켜지고, 실행 경로에 “샤드 키” 단계가 생긴다. 샤딩을 안 쓰면 그 단계와 규칙이 통째로 사라지고 화면이 단순해진다.

자동 감지(커넥션 팩토리 인자에 userNo류가 있는지)를 먼저 해 보고, 확신이 없으면 설정을 채우라고 안내한다. 잘못 켠 채로 오탐을 쏟는 것보다 낫다.

다만 샤딩을 안 써도 남는 문제가 있다 — 요청 본문의 userNo를 검증 없이 WHERE 조건에 넣으면 남의 데이터를 읽는다. 그건 SHARD-005가 아니라 별도 규칙(AUTHZ-001, 후보)으로 보는 것이 맞다고 본다. 필요하면 이번 범위에 넣겠다.

6. 판정의 근거를 항상 같이 보여준다

우측 상세에는 항상 근거 체인(값이 어디서 흘러왔는지, 어떤 역연산을 찾았는지/못 찾았는지)과 확실 / 추정 표시를 같이 둔다. 추정은 “확실한 것만 보기” 토글로 접을 수 있다.

랭킹 집계처럼 일부러 그렇게 짠 코드가 있다. 항목마다 “의도된 것으로 표시”를 두고 .tracelens/db-baseline.json에 심볼 기준으로 남긴다(줄이 밀려도 유지되고, 코드가 바뀌면 다시 뜬다).

7. 점검 규칙 초안 — 무엇을 어디까지 정적으로 잡을 수 있나

“정적으로 확실”은 Roslyn 심볼·데이터 흐름만으로 판정 가능한 것, “추정”은 값이 런타임에 정해져 힌트만 줄 수 있는 것이다. 샤딩 전용 표시가 붙은 규칙은 샤딩을 쓰는 솔루션에서만 켜진다.

8. 설정 초안 — 사내 DB·캐시 계층을 알려주는 부분

“쓰기인지 읽기인지”, “무엇이 역연산인지”는 프레임워크마다 다르다. 아래를 tracelens.config.json에 한 번 적어두면 그다음부터 자동으로 따라간다. 자동 인식이 실패하면 “접근 지점을 못 찾았다”가 아니라 “이 설정을 채워라”를 화면에 띄운다. 

"db": {
  "connectionFactories": [
    "GameServer.Data.IShardConnectionFactory.OpenAsync(int userNo)",  // 첫 인자가 샤드 키 (샤딩을 쓸 때만)
    "GameServer.Data.IDbConnectionFactory.OpenAsync()"
  ],
  "queryApis": ["Dapper.SqlMapper.*", "GameServer.Data.DbExtensions.ExecProcAsync"],
  "dataSources": {
    "GameDb":   { "kind": "shard", "shardCount": 8, "shardBy": "userNo % 8" },   // "single" 이면 SHARD 규칙군이 꺼진다
    "GlobalDb": { "kind": "single" },
    "LogDb":    { "kind": "single", "writeOnly": true }
  },
  "schemaFiles": ["db/schema/*.sql"],
  "compensation": {                                  // 보상 처리 판정에 쓰는 역연산 짝
    "pairs": [
      { "do": "INSERT user_item",  "undo": "DELETE user_item" },
      { "do": "AddItemAsync",      "undo": "RemoveItemAsync" },
      { "do": "IncreaseAsync",     "undo": "DecreaseAsync" }
    ],
    "irreversible": ["*.PushClient.SendAsync", "*.MailSender.*", "*.BillingClient.GrantAsync"],
    "idempotent":   ["*.Cache.RemoveAsync", "*.LogRepository.*"]   // 남아도 무해 / 재실행 안전
  }
},
"redis": {
  "clientApis": ["StackExchange.Redis.IDatabase.*", "GameServer.Cache.IGameCache.*"],
  "keyPatterns": ["user:{userNo}:*", "guild:{guildId}:*", "lock:*", "session:{token}"],
  "requireTtlFor": ["session:*", "lock:*", "attendance:*"]
}

9. 기존 보기와의 연결

  • 호출 흐름 / 전체 흐름도 — 저장소에 닿는 메서드 노드에 배지를 단다(GameDb Redis). 진입점 목록에는 “커넥션 수 · 트랜잭션 유무”를 붙인다.
  • 클래스 다이어그램 — 리포지터리 박스에 다루는 테이블·키 수를 표시한다.
  • 시작 흐름 — 커넥션 팩토리·IConnectionMultiplexer의 수명 등록을 이미 읽고 있으므로 CONN-002는 거기서 그대로 가져온다.
  • 미들웨어 보기 — 미들웨어가 여는 Redis·DB 접근도 같은 규칙으로 검사해서 양쪽에 함께 띄운다(예: RateLimit의 INCR).

확인이 필요한 것

  • DB 접근 방식 — Dapper / EF Core / 자체 래퍼 / 저장 프로시저 중 무엇인가? 프로시저 위주면 “테이블 매트릭스”가 “프로시저 매트릭스”가 된다.
  • 보상 코드의 관용 형태 — 되돌리기를 catch에서 하나, 별도 Rollback*/Restore* 메서드로 빼나, 아니면 재시도 큐에 넣나? 이름 규칙을 알려주면 정확도가 크게 오른다(compensation.pairs).
  • Redis 클라이언트 — StackExchange.Redis 직접 사용인가, 사내 래퍼인가? 래퍼면 메서드 이름 → 명령(GET/SET/DEL/INCR) 매핑이 필요하다.
  • 샤딩 사용 여부 — 지금 대상 솔루션은 쓰나? 쓰면 샤드 선택이 인자 전달인가, 컨텍스트(AsyncLocal)인가?
  • DDL(schema.sql)에 접근 가능한가? 없으면 IDX-*·MAP-* 규칙군은 빼야 한다.
